Onboarding step dots & blocking save
DQStepDots — 7 steps, on step 3
6pt dots, 6pt gap. Current elongates to a 20×6 pill — that is the only difference between states, so it never reads as a meter. Done text-3 · current text · upcoming track. Neutral throughout. No ember, no fill sweep, no connecting line. Centred, 12pt under the top bar, 24pt above content. Width animates .28s ease-out; colour crossfades with it. No “3 of 7”. The dots are the count. A mono readout beside them says the same thing twice. Not tappable. Progress display only — back is the top bar's job.
DQBlockingSave — commit, not fetch
Creating your profile… This takes a moment. Keep the app open.
Skeleton vs spinner is fetch vs commit, not duration. A fetch has a known shape, so it skeletons. A commit has no incoming shape — the user is leaving the screen — so it spins. Scrim + 14pt blur over the form it is committing, form left visible beneath at reduced contrast. Card r-card 24, surface, 24/26 padding, min width 196, shadow. Spinner 22pt, 2pt stroke, track ring with a text head, .8s linear. Never ember — ember is not a waiting colour. No cancel, no progress bar. If it can be cancelled it is not blocking; use an inline field state instead. Min on-screen 400ms so a fast save does not flash. Past 8s the sub-line swaps to “Still working — you can keep waiting or try again later”, never a silent hang.
